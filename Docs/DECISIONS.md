# Shadow Steps — decisions log

Each decision records context, the choice, and what it rules out. Newest at the bottom.

## D-001 Reference simulation is law for levels 1–20
reference/build.py and reference/DESIGN.md define the rules. `GuardSchedule`, `VisionSystem`, `RulesEngine` and `Solver` are line-by-line ports. Quirks are preserved on purpose, notably:
- Guard phase is stored modulo the level period (lcm of guard cycles). Travel-facing guards (`patrol`, `loop`) derive facing from the previous phase, so at phase 0 after a wrap they show their *authored* facing, not their travel facing (level 10 guard A is the visible case). Tests pin this.
- The reference `cone_visible` returns true for the guard's own tile; `GetVisionCells` excludes it for display only. Occupancy is checked before vision anyway.
- Line of sight is a 12-samples-per-tile centre-to-centre walk; cells touched by the sample that are walls (or the locked door) block, endpoints excluded. No physics raycasts in logic.
Any future rule change must: update build.py, regenerate/re-solve, update validation.json, and bump `format_version` if data shape changes.

## D-002 Hand-written JSON parser instead of JsonUtility or Newtonsoft
levels.json uses nested arrays (`[[x,y],...]`), `null` for key/door and will need dictionaries for saves. `JsonUtility` cannot deserialize any of these. Newtonsoft (com.unity.nuget.newtonsoft-json) is not installed and the spec prefers no new dependencies. `MiniJson` (~300 lines, ordered objects, strict errors with char positions) lives in the engine-free Data assembly, so loaders are testable with plain dotnet. If a future need outgrows it (streaming, huge files) swap behind `LevelPackLoader`/`SaveSerializer` only.

## D-003 Assemblies and dependency direction
`Core` (no UnityEngine) ← `Data` (no UnityEngine) ← `Runtime` ← `UI` ← `Editor`. Tests.EditMode references Core + Data only, so it also runs under dotnet (Tools/run_core_tests.sh). Presenters subscribe to `TurnResult` events and never write game state.

## D-004 Solver is driven by RulesEngine.Step
Instead of a second copy of the rules, the C# BFS expands states through the same `Step` the game uses, in the reference action order with a FIFO queue. Parity tests show identical paths and identical explored-state counts to Python for all 20 levels, which validates both the engine and the solver in one go.

## D-005 Gadget "requirement" is a measured fact, not a claim
Constrained solves (see PROGRESS.md M1 table) show smoke is strictly required on levels 11, 17, 19, 20; level 14 ("Smoke and Mirrors") has an 11-move solution without smoke; EMP is never strictly required (12, 15, 18, 20 are solvable without it at the same length). Per CLAUDE.md the 20 levels are not changed. Level 14 and the EMP levels are flagged as "design intent, not proven" in KNOWN_ISSUES.md for the human playtest; the tutorial copy must not claim EMP is required.

## D-006 Verification strategy while the Unity GUI is open
Unity batch mode refuses to start while the editor holds the project lock. Until the user closes the editor (or runs the Test Runner manually), compile/test evidence comes from: (a) dotnet build of Core/Data/tests, (b) dotnet build of Runtime/UI/Editor sources against the Unity managed DLLs in Library/ScriptAssemblies (from M2 on), and (c) the editor's own Console after refresh. PROGRESS.md states which of these produced each claim.

## D-007 Deterministic .meta files
`Tools/gen_meta.py` writes metas with GUIDs derived from the asset path so scripts, folders, asmdefs and JSON can be committed before Unity imports them, and so GUIDs never churn between machines. Unity may add importer fields later; that is harmless.

## D-008 Save file format
Single JSON file in `Application.persistentDataPath/shadowsteps_save.json`, written via temp file + `.bak` rotation. Load order main → backup → defaults, keeping a `.corrupt` copy. Versioned (`version: 1`); unknown/missing fields fall back to defaults; newer versions are rejected rather than guessed.

## D-009 Product naming
The Unity project folder/product name is still "Stealth Escape" from project creation. Code, scenes and assets use the game name "Shadow Steps". `productName`, bundle ids and icons are changed together in M8 so a half-renamed build never ships.

## V2 decisions

## D-010 Legacy door becomes locked incoming edges plus an occluding node
V1 modelled the door as a tile that blocks the player and sight until the key is held. V2 edges carry locks, so `LevelGraph.BuildLegacyGrid` locks every edge *into* the door node and `LevelDefinition.Door` keeps the node as a sight occluder while the key is not held. Edges *out* of the door stay open. This reproduces V1 exactly (proved by the 20/20 replay and solver parity) and is the shape the migrator exports.

## D-011 Guard routes need edges, not permissions
A guard segment is legal when an edge exists in the travel direction (ping-pong routes also need the reverse edge, loops need the closing edge). Locks are ignored for guards: legacy levels 10 and 19 patrol through the door node. Guards moving through walls or missing nodes are errors.

## D-012 Guard overlap policy
Two guards sharing a node at the same phase is an **error** for schema-2 levels (LEVEL_DESIGN_PARAMETERS §5 default: reject rather than invent AI) and a **warning** for migrated legacy levels, because level 18 ("Shift Change") does it at phases 1, 5, 7, 11. Level 18 is scheduled for redesign in V2 M5.

## D-013 Independent cadences generalise the legacy step
`moveEvery` and `rotateEvery` replace the single `step`. Position uses `phase / moveEvery`, scheduled rotation uses `phase / rotateEvery`, travel facing derives from the previous movement update. With both equal to `step` the schedule and the period are identical to reference/build.py (tested for all 20 levels), so the phase-0 facing reset quirk is preserved.

## D-014 Schema 2 shape and loader policy
Root `schemaVersion: 2` with `levels[]` (or a single level object for editor exports). Board: `width`, `height`, `nodeSpacing`, `nodes`, `walls`, `cover[{pos, traversable}]`, `edges` = `"autoCardinalExceptBlocked"` with `blockedEdges`/`lockedEdges`, or an explicit `[{from, to, type: open|locked|oneWay, bidirectional}]` list. The writer always exports the explicit expanded list. Unknown fields warn; unsupported features (switchable edges, switches, decoy charges, cone angles other than 90, objectives other than reachExit) are rejected with a path so no content can depend on them silently. Legacy `format_version: 1` files still load and are migrated in memory with conversion notes that are exported with the level.

## D-015 Vision occluders are nodes only
`VisionSystem.BlockedPredicate` tests node flags (walls, cover) plus the locked door. Edges are never consulted, which satisfies "a missing edge stops movement but does not block sight" and is covered by a dedicated test.

## D-016 Restrictions actually simulated
`noWait` is enforced by `RulesEngine.Validate` (so the solver honours it). `maxMoves`, `noUndo`, `requiredGadget` are stored for UI/analysis only; the validator warns that `maxMoves` is not enforced. `smokeTurns` is configurable (default 2); `empTurns` must be 1.

## D-017 Tutorial pack and catalog merge
The five V2 tutorial levels live in their own schema-2 file (`levels_tutorial_v2.json`, ids 101–105, world 1 chapter 0). `AppServices` merges packs in a fixed order (tutorial, then legacy `levels.json`) into one catalog and rejects duplicate ids. Keeping files separate means the legacy file stays byte-identical to the reference while new content is authored freely. Level ordering in menus follows catalog order, not numeric id.

## D-018 Fresh traces are the only validation evidence
`validation_tutorial_v2.json` (and later `validation_v2.json` for the legacy set) is generated by the C# solver (`--export-validation`) and consumed by replay tests that also assert the solver still returns the same path and explored-state count. No trace is ever hand-written. Mechanic necessity (`WaitRequired`, `SmokeRequired`, `EmpRequired`, structural `KeyRequired`) is stored alongside and asserted per level.

## D-019 Authoring model lives in Data, the window only draws
`LevelAuthoringModel` holds all editing rules (edge cycling, resize, auto edges, conversion) so they run under dotnet tests; the EditorWindow is a thin IMGUI layer. The random wall search in the runner is a designer aid and never ships content automatically: every candidate must be inspected and committed by hand.

## D-020 Shipped pack is schema 2; the reference stays V1 (superseded by D-026 for content)
`Assets/StreamingAssets/ShadowSteps/levels.json` is generated (`--migrate`) from `reference/levels.json` plus the documented level-18 patch and is never hand-edited; `reference/` is immutable V1 evidence. If a legacy level is changed again, the change goes into the exported file via the Level Editor and the diff is recorded in PROGRESS.md and in that level's `conversionNotes`.

## D-021 Level 18 redesign choice
Among the measured variants, moving the patrol to row 1 was the only one that removed the overlap *and* preserved the original 14-move solution and gadget/WAIT profile. Visual readability of the top row (rotating guard alone) improves as a side effect.

## D-022 Unlocking by catalog order
Unlock state is derived from completion records and the catalog order (`Progression.IsUnlocked`): a level is open when it is first in the catalog or its predecessor is completed. `SaveData.HighestUnlockedLevelId` is still written for compatibility but no longer decides anything, so packs can be reordered without migrating saves.

## D-023 Screens self-build; prefabs are generated from the same code
Every screen implements `BuildHierarchy()`; `UiPrefabSet.Create<T>` instantiates the prefab when assigned and otherwise builds the screen at runtime. The setup menu generates the prefabs by calling the same method, so designers can restyle prefabs in the editor while the fallback keeps the game runnable without any generated assets (important for tests and for a fresh checkout).

## D-024 Procedural audio until licensed assets exist
`AudioService` synthesises short tones and an ambient pad at startup (original, licence-free). Clips are addressed by the `Sfx` enum so real recordings can replace them later without touching callers. Audio never influences simulation.

## D-025 Detection is a per-level rule; V2 means "seen before or after the guard move"
Design change (2026-10-28, revised the same day from "before and after" to "before or after" on the user's correction): after the player acts, a cone captures if the player's landing node is inside guard vision at the guard poses before the phase advance **or** at the poses after it. Stepping into a cone is always lethal, even if the guard turns or walks away on that turn. "Guard vision" is the union of all cones. The guard reported as captor is the one that sees the player after the move, else the one that saw the node before. EMP freezes the phase, so both looks are identical; smoke conceals both looks.

The rule is stored on the level (`rules.detection`: `beforeOrAfterGuardMove` | `afterGuardMove`) rather than hard-coded so that:
- schema 1 files (and `LevelDefinition`'s legacy constructor) keep V1 semantics, which keeps the Python parity suite meaningful as proof of the engine port;
- schema 2 files default to the V2 rule and the shipped packs state it explicitly;
- `--migrate` preserves semantics (a V1 file converts to `afterGuardMove` with a conversion note) and `--migrate … v2rules` opts into the V2 rule.

Consequence: V2 is never more lenient than V1 (tested over the reachable state space of all 20 levels). The V1-era content relied on entering a cone as the guard turned away, so under the V2 rule only levels 1, 4, 12, 14 and tutorial 101 remain solvable; the rest are recorded as unsolvable (`"moves": -1`) in the validation files and carry no par. Content redesign is a separate task (KNOWN_ISSUES #18). The validation export now records unsolvable levels instead of refusing, so the shipped data always states the truth under the active rule.

## D-026 Content is generated from curriculum specs by the C# engine; the V1 reference is history only
The before-or-after detection rule (D-025) left 20 of 25 levels unsolvable, so the shipped packs are now produced by `Tools/CoreTestRunner/Generator.cs` from `Tools/LevelSpecs/*.json`: per level a size, guard templates (mode, range, cadence, route length), gadget charges, key/door, wall/cover/one-way counts, a required mechanic and a par band. The generator randomises within those ranges (deterministic seed) and keeps the best candidate that the real validator, solver and constrained solves accept, scoring for a unique shortest solution, a par in the upper half of the band, little dead space and no long idles. Levels 1 and 4 are kept from the migrated reference because they already fit the curve; 101 is kept as authored. `reference/levels.json` remains V1 evidence for the engine port and is no longer the source of the shipped content. The curriculum and all measured numbers are in `Docs/LEVEL_CURRICULUM.md`; the tests assert the measured mechanic sets so any regeneration is a deliberate change.

Why a generator rather than hand-authoring: 20 levels under a new rule needed to be provably solvable with proven mechanic necessity and a monotonic curve; the solver is the only reliable judge of that, and the specs make the design intent reviewable. Hand polish still happens in the Level Editor (export, edit, re-validate).

## D-027 V3 rules live in a new core (`ShadowSteps.V3`) beside the V2 core until the runtime switch is proven
The 2026-10-29 handover replaces guard cones with 2-node straight sight, adds wall cameras with a lockdown budget, turns doors into connections opened by crossing, makes Smoke a stationary cloud and EMP a camera disable, both free and targeted, and changes the turn order. Rewriting the V2 files in place would have broken the 206-test V1/V2 safety net while the new engine was unproven, so the V3 engine is a parallel namespace in the same engine-free assembly: `Stage`, `StageState`, `StageRules.TryApply` (the one transition used by runtime, preview and solver), `GuardTrack`/`CameraTrack`, `Sight`, `StageSolver`, `StageMetrics`, `StageValidator`, `StageJson`, `BrowserLevelImporter`. Prototype behaviours are ported exactly where the handover does not override them (camera footprint starts one node out, ping-pong endpoint facing, `budget || 4`). Once the Unity runtime runs on V3, the V2 core, its tests, generator and packs move out of the project (they are already backed up under `reference/`).

## D-028 Browser values are fixtures; the C# solver is the authority for pars and Ghost
`levels_v3.json` stores par, 3★/2★ thresholds and `ghostOffered` as written by `StageMetrics` (0-1 BFS, free gadgets). The browser export's `par`/`ghostOffered` and `playtest_validation_report.json` are kept only to assert parity (30/30 today). Any rule or data change re-exports scoring with `--v3-import` or `--v3-export-validation`; tests fail until the stored values match the solver again. The star formula is the provisional v3 one (`T3 = P + max(1, min(3, ⌊P/10⌋))`, `T2 = P + max(2, ⌈0.3P⌉)`) and is isolated in `StageScoring` for final tuning.

## D-029 V4 blocked cover is a third cell kind, not a wall and not a cut
The 2026-10-30 handover adds `X` cells (55 across 25 stages). They are modelled as `Stage.Blocked`: non-walkable (`IsFloor` false, so no node, no connection, no smoke target, no guard route, no key/exit/start) and fully opaque (`Stage.Occluders` = walls ∪ blocked feeds the one `Sight.Obstructed` routine, so guards, cameras, smoke throws and previews all treat the whole cell as solid, corner contact included). Walls remain '#' and may host cameras; blocked cover may not. Missing connections (`cuts`) remain sight-transparent. Rows are authoritative; the importer fails with the exact cell when `blockedNodes` disagrees, and unknown characters fail with coordinates. Routes are imported exactly as serialized (no re-extension). The shipped pack is now `levels_v4.json` / `validation_v4.json` (schema 3 unchanged); the V3 pack is kept in `reference/v3_shipped_backup_2026-10-30/`. Rendering uses a crate placeholder drawn slightly smaller than the cell while the rule uses the full cell (handover §2.1).

## D-030 The 3D presentation is an adapter over the unchanged engine, selected per scene
`ShadowSteps.Art3D` is its own assembly (refs Core, Data, Runtime). It builds geometry from the same `Stage` objects the
game loads, mirrors `GameSessionController` events exactly like the HUD, and draws only cells supplied by `Sight` and poses
supplied by `GuardTrack`/`CameraTrack`. It never raycasts for visibility, never simulates schedules and strips colliders
from every instantiated mesh so decoration cannot intercept input. The 2D sprite board stays the default; the composer's
`Use3DPresentation` flag plus a palette asset switch a scene to 3D, and `InputController` exposes picking overrides so the
angled camera resolves taps by intersecting the floor plane. Models are referenced only through `SS3DArtPalette`, so any
mesh can be replaced without touching level data or code. The starter package's DTO/Newtonsoft reader and its re-extension
logic were not adopted: the engine's `StageJson` is the single source of level data.


## D-031 Rendering quality comes from URP features first; prop quality needs real assets
The milestone 3 courtyard did not approach the mock art because the gap is in the props (sculpted trims, foliage, water
shader, texture work), which procedural chamfered boxes and the starter kit's untextured models cannot close. Rather than
keep adding procedural blockouts, the project upgrades what every frame gets for free: a narrow-FOV perspective camera,
ACES tonemapping, bloom, colour grading, vignette, depth of field on the perimeter, SSAO, soft shadows and a generated
stone albedo. All of it is adapter-side (`ShadowSteps.Art3D`) plus URP settings written by an editor menu, so swapping
the props later (purchased stylized kit or Blender hero models, the user's choice) changes nothing in gameplay or in this
pass. Post-processing values live on the palette asset so artists tune them without code.

## D-032 Hero environments are authored layouts, not seeded generators; review frames are rendered headlessly in a project clone
The ten seeded town profiles (D-031 follow-up) could not reproduce the approved mock: random prop scatter never yields a composition, and a generator written for yaw 0° cannot reason about what a 45° camera shows. The Town Plaza is therefore a `TownPlazaLayout` asset: every object is an authored placement anchored to the plaza edges in tile units, so the same composition survives a different board size, while the grid, nodes, cover and actors stay data-driven from `levels_v4.json`. Prefab mapping is documented per placement (mock element → prefab → pack). Because the Unity GUI holds the project lock, visual review no longer waits for the user: `Tools/render_batch.sh` runs editor methods in a scratch clone (`../StealthEscape_render`) with graphics enabled and writes PNGs, which closes the "calculated, not rendered" gap of milestones 3–6. The clone is disposable and outside git; generated scene/asset/meta files are copied back explicitly.

## D-033 The 2D art layer is a third adapter, generated from code, over the same engine and layout
Replacing the 3D presentation with 2D artwork did not change the architecture: `ShadowSteps.Art2D` mirrors `GameSessionController` exactly like the 3D bridge and the placeholder board, draws only the cells and poses the engine reports, and reuses the runtime `BoardLayout` so tap/swipe picking and the camera fit are byte-identical. Art is generated, not hand-painted: board/object sprites are procedural PNGs (original, replaceable per slot in `SS2DSpriteLibrary`), and the characters are frames captured from the character pack the game already owns, so no 3D model, Synty prefab or glb is referenced at runtime. The placeholder `BoardView` stays as the default and as the fallback; the new layer is switched on per scene (`Use2DArtPresentation`).

## D-034 Level completion is a presentation hook after the win is recorded; the door is visual, the exit node stays logical
The exit node remains the engine's exit (rules, solver and scoring untouched). The 2D presentation adds a door beyond the board edge the exit sits on and a completion sequence (walk to the door, open, enter, close, next stage). To keep progression authoritative, `GameFlowController` records the win first and only then calls `GameSceneComposer.WinTransition`; a presentation that returns true owns the remaining choreography and either advances to the next stage or invokes the supplied results continuation. The placeholder board and the 3D layer do not set the hook, so their flow is unchanged. All art is addressed through `SS2DSpriteLibrary` slots so final assets replace placeholders without touching gameplay or the renderer.

## D-035 Cameras watch the node directly in front of the lens; camera-stage content follows the C# solver, not the browser prototype
User decision 2026-11-03 ("option 2"): a wall camera must cover the node right in front of it. `Sight.CameraFootprintStart` is now 0, so the 3-wide × 2-deep footprint starts at the lens node (the adjacent floor node) instead of one node out; occlusion, smoke, EMP, cover and door rules are unchanged. The old blind spot was a rounding artefact of the browser prototype, not a design intent. Consequences accepted: LEVEL-18 (rotating, now counter-clockwise, crates at (4,2),(3,3), start (1,3)) and LEVEL-19 (sweeping, crates at (4,1),(1,3), start (1,1)) were redesigned because they had no solution; LEVEL-23 gained one corridor node (exit (5,2)) and LEVEL-25 two (exit (6,2), budget 1) so EMP, and Smoke on 25, stay mandatory as their briefs promise; LEVEL-16/20/24 lose their Ghost route and become forced-alarm stages; LEVEL-20 par 10 → 6. Browser par/Ghost parity is therefore asserted only for the 22 stages without cameras; all camera-stage scoring comes from `--v3-export-validation` into `validation_v4.json` and the `scoring` blocks of `levels_v4.json`. The alarm-budget validator keeps its ≥ 1 rule (a budget of 0 was tried for LEVEL-25 and rejected by `StageValidator`).

## D-036 Camera detection is a 70° cone from the wall face, two spacings deep; the drawn cone is the engine's traced silhouette
User brief 2026-11-03 ("Implement Final Cone-Based Camera Vision"). `Sight.CameraVision` now detects a floor node when its centre has a positive forward projection ≤ 2.0 on the facing from the wall-face origin (wall cell + ½ toward the mount face), its lateral offset is within 35° (|lateral| ≤ forward·tan 35°), and the segment origin→node centre crosses no wall, solid cover, closed door or smoke cloud (strict corner contact; the camera's own mounting wall is ignored). Boundary comparisons use one tolerance (`ConeTolerance` = 1e-6). This replaces the 3×2 rectangle (D-035) and gives a T-shaped footprint on an open floor: the lens node plus three nodes of the second row; nodes beside the lens (63°) and the third row (forward 2.5) are outside; a camera facing along its wall sees the two nodes along it; facing into its wall it sees nothing. The 2D overlay no longer merges cells: `Sight.CameraConeOutline` traces 49 rays through the same occluders (`RayDistance`) and the renderer draws that fan, so the drawn cone, the lens direction and the ring-marked detected nodes always agree; a disabled camera has no cone. Guard vision, EMP/lockdown timing, rotation/sweep schedules and previews are unchanged (they consume the same `CameraVision`). Level data was deliberately not changed: the measured impact and proposed corrections are in `Docs/Reports/CAMERA_CONE_VALIDATION_2026-11-03.md` and await approval.

## D-037 Every level limits WAIT (`waitLimit`), enforced by the rules and respected by the solver
User request 2026-11-03. `Stage.WaitLimit` (JSON `waitLimit`, −1 = unlimited for fixtures/legacy) caps WAIT actions per attempt; `StageState.WaitsUsed` counts them (moves and free gadgets do not), `StageRules.TryApply` rejects a WAIT past the limit with `RejectReason.NoWaitsLeft`, and the solver keys its states by waits used whenever a limit (or an analysis cap, `SolveOptions.MaxWaits`) is in force. `StageMetrics` now reports the WAITs in the par solution, the smallest WAIT cap that still reaches par (`MinWaitsForPar`) and the shortest win without any WAIT. Initial limits written into `levels_v4.json` by policy **max(3, MinWaitsForPar + 2)**: 3 on every level except LEVEL-4 and LEVEL-7 (4), so every par solution stays reachable with at least two spare WAITs; no par, Ghost or gadget flag changed (verified by re-export). LEVEL-23 (unsolvable under the pending cone rule) used the WAIT count of its shipped solution (0). The HUD shows the remaining WAITs as a badge on the WAIT button and disables it at zero.

## D-038 A locked edge opens only when the key-holder crosses it; closed doors block movement and sight until then
Found while importing Levels 26–30 (2026-11-03). The engine had opened a locked edge as soon as a key-holder arrived at either endpoint (V3 handover reading "door stops blocking sight once the key is held"), one step before the crossing. The import kit's rules say the key "opens each crossed locked edge" and "closed doors block movement and sight"; the kit's reference engine behaves that way, and on Level 30 the early opening let a sweeping camera see the player through the door one step early (par 29 vs 28, Ghost 36 vs 28). Measured with a switch (`StageRules.DoorsOpenOnApproach`): all 30 shipped levels have identical par, Ghost and gadget flags under both rules (their doors are never watched through), so the crossing-only rule is now the default. The switch stays for measurement; the door tests were rewritten for the new semantics.

## D-039 One zoom for the whole pack: every level is framed at the largest grid
Requested by the user (2026-11-04, "when level is small, everything looks big"; "keep the same look as largest grid for small grid"). `SS2DCameraFitter` fitted each board to the HUD band, so a 3×3 tutorial drew nodes and characters about twice the size of a 7×5 level and over three times the size of the 9×11 finale. The fitter now frames every level at least as wide and tall as `referenceGridNodes`, which the session bridge and the art preview set to the loaded pack's largest grid in portrait orientation (short side × long side; 9×11 today, `LargestPortraitGrid`). The largest level is framed exactly as before; smaller boards sit centred with more courtyard around them. `FitBackground` frames the painted ground at the same reference grid so the courtyard scale is also constant. Trade-off: on small levels with an all-wall boundary ring the painted courtyard wall no longer coincides with the hidden logical ring (KNOWN_ISSUES #50). `referenceGridNodes` 0×0 restores the old per-board fit.

## D-040 Global Stealth / Knockout modes on every level; knockout = move onto an adjacent guard from behind or a side, one counted action
From the user's global-modes handoff (2026-11-04), superseding the Level-26-only prototype scope. The rules mode lives in `StageState.Mode` (set by `StageState.Initial(stage, mode)`), so previews, the solver, retries and any resumed run carry it; `StageState.Defeated` is a 64-guard bitmask over stable guard indices (validator caps guards at 64). In Knockout mode `StageRules.TryApply` normalises a Move whose target holds a live guard into `StageAction.Knockout(i)` (token `KO#i`), so a tap on the guard, the direction and an explicit request are one action; `CheckKnockout` evaluates the guard's CURRENT pose (never its next step): connected, door-free (a key does not help), not frontal (smoke does not help). The knockout is then resolved by the ordinary counted pipeline as the move onto the guard's pre-update node with the target removed, so survivors can see or collide with the player at the landing node before or after their update, gadget durations tick once, a camera can observe it, and lockdown/exit priority are unchanged. Stealth is byte-for-byte the old pipeline (every Stealth solution replays identically under Knockout rules, `V3KnockoutTests`). No level, guard, camera, door, charge or budget was changed. Selection: HUD toggle on every level (plus "retry/replay in the other mode" on the failure and results cards); switching restarts the current level from its authored state without counting an action or advancing; selecting the active mode is a no-op; Retry, Next Level, the level picker and a fresh scene keep the remembered mode (`SaveData.SelectedMode`, Stealth when never saved). Records are per (stable level id, mode, rules version `knockout-move-v2`): `SaveData.Results` stays the Stealth table (legacy untagged results load as Stealth), `KnockoutResults` is separate, unlocks and completion are shared, resume is shared. Knockout pars come from the C# solver on the actual layouts (`--v3-knockout-pars`, stored as `scoring.knockoutPar/knockoutThreeStar/knockoutTwoStar`); a level without them falls back to the Stealth par, which every Knockout run can also reach. No HP, stun, noise or new rewards.

## D-041 Guard first-encounter cards: one short card per behaviour, once per behaviour per mode, replacing the overlapping tutorial intro
From the guard-FTUE addition to the global-modes handoff (2026-11-04, `guard_ftue_messages.json`, tutorial version `guard-types-v1`). `GuardOnboarding` (Data) holds the copy and builds the queue from the ACTUAL live guards of the loaded board (static, rot, bounce, loop order; one card per behaviour; knocked-out guards are not targets; guard-free boards give nothing) minus the acknowledgments for the current mode. Acknowledgments are stored in the existing `SaveData.SeenTutorials` list under `guard:guard-types-v1:<type>:<mode>` (legacy saves have none = unseen; no serializer change, no unlock or completion effect) and are set on "Got it" only. `GameFlowController` shows at most ONE message per level visit (user decision 2026-11-04, "don't crowd it"): a first-encounter guard card when the level introduces a new behaviour (the level's own intro is dropped when it only explains that guard - FTUE-3/4/5 - and deferred to the next visit otherwise), else the level intro once; a mode switch may show the other mode's one card; remaining unseen behaviours wait for a later level; the representative guard is tinted through `GameSceneComposer.GuardHighlight` (2D bridge) or the placeholder board. Mode switch / retry / stage load cancel the queue and rebuild it for the new board context; a board-session token plus the card's mode and identity make a stale "Got it" a no-op. No gameplay state is touched by opening or dismissing a card (PlayMode check compares the full state key).

## D-042 Camera cone graphics show the full nominal cone; detection keeps its occlusion

## D-047 Long edges: passage cells, so not every square holds a node
User rule (2026-11-05, during the LEVEL-1..3 review): "we shouldn't always keep nodes on each square; sometimes the distance between nodes can be 2x or 3x a square". Supersedes the "no variable-length edges / uniform nodeSpacing along a route" lines of `LEVEL_DESIGN_PARAMETERS.md` §1 and `V2_CHANGE_CONTROL.md` for schema-3 packs. Implementation keeps the grid (coordinates, portrait fit, camera cones, cover and walls are untouched) and adds **passage cells** to the rows: `-` carries a horizontal connection, `|` a vertical one, `+` both. A passage holds no node: nothing stands on it, it never occludes sight, and it is skipped by `Stage.Step(from, dir)`, which returns the next node that way, so one edge can span 2 or 3 squares. Rules: one counted action traverses one edge whatever its length; cuts and doors are keyed by the two end nodes (so a long edge can be cut or locked); a knockout is legal from the far end of a long edge, with front/back/side judged by the nodes the guard faces and flanks (`Step`), never by raw adjacency; patrol routes may step a long edge in one turn and the guard faces along it; guards see **two nodes** ahead (the taught rule), looking across passages, so the drawn fan reaches the second seen node even when it is 4+ squares away. Rejected alternative: range in squares (a 3-square walkway would hide its far node, contradicting "sees two nodes ahead"); it is a one-line change in `Sight.GuardVision` if playtests want it. The validator rejects passages that do not join two nodes along their axis, passages used as start/exit/key/route nodes, and cuts between nodes that are not one straight run apart; a cut touching a non-node cell is a no-op warning (legacy packs had one on LEVEL-1). Tap input: a tap moves only to the next node in that direction (`Stage.DirectionTo`), so tapping the far end of a long edge works and tapping a node two edges away does nothing. Applied to the redesigned boards: LEVEL-1 now has 2-square edges on its outer rows (the bottom walkway is the quickest way round the guard: knockout par 6, still no route without the knockout), LEVEL-2 on its top row (par 8 / 10 without a knockout unchanged), LEVEL-3 drops the dead-end node above its right cover crate and the no-op cut that touched the crate below it (a gap, not a walkway, because every long edge tried on a route to the corridor handed the player a free tempo against the patrol and a knockout-free 11-move route appeared; par 8, knockout still mandatory).

## D-049 Sparse boards: empty ground and the sparsifier
User direction (2026-11-05, on LEVEL-8): "reduce more nodes, they feel unnecessary; make the edges longer", then "do this for all the other levels". Two additions. (1) A third non-node cell, `_` = empty ground: no node, no connection through it, transparent to sight (like a passage without an edge). It lets a board keep its grid and its open courtyard look while holding only the nodes that matter, where a wall would have blocked sight and a passage would have carried an edge. (2) `--v3-sparsify <pack> <out> [skipCodes] [maxRun]`: for every stage, greedily take nodes off the board, restarting after each accepted removal.
